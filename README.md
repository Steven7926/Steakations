# Steakations: https://stevenlaurensteakations.com/
### This is a small wordpress blog site outlining steakhouse reviews by me and my Fiance. I made this website to learn Wordpress and small, cheap, website hosting
- The entire site is hosted on an private S3 bucket and served through a Cloudfront distrubution as a static website, making the cost pennies a month.
- The static files are generated by mirroring the locally-running site with `wget` (see "Generating & Deploying the Static Site" below) rather than the Simply Static plugin — Simply Static runs its crawler *inside* the wordpress container, and `WP_HOME`/`WP_SITEURL` (`localhost:8085`) isn't reachable from inside that container (it only listens on port 80 internally), so it could never fetch its own pages. `wget` runs from the host, where `localhost:8085` is reachable, sidestepping the problem entirely.


## To Run Site Locally:
  1. Git Clone Repo
  2. `docker compose up -d` from the root directory.
     - This brings up an `init` job alongside the site that does everything the manual setup used to require: installs WordPress core, drops the tables the content backup will recreate and imports `steakations_backup.zip`, writes the permalink rewrite rules, copies `./images` into `wp-content/uploads` at the paths recorded in the backup's `guid`s, and installs+activates whatever plugins the backup's `active_plugins` option expects (from wordpress.org, matched by slug).
     - It's idempotent — every step checks whether it's already done, so re-running it (`docker compose up -d --force-recreate init`) after adding new images or if a plugin ever goes missing is safe and just fills in whatever's missing. Check `docker compose logs init` if something looks off.
     - `wp-content` (uploads, plugins, themes) lives in the `wp_content` Docker volume, and WordPress core itself in `wp_core` — both are local to this machine and never travel through git, which is exactly why `init` exists: a fresh clone always starts with empty volumes, and this job is what reconstructs them the same way on any machine.
  3. Access http://localhost:8085/
      - Site dashboard is at http://localhost:8085/wp-admin/ — log in with `WP_ADMIN_USER` / `WP_ADMIN_PASSWORD` from `.env`.
  4. Access phpmyadmin at http://localhost:8081/ if you need to poke at the database directly (root user, `MYSQL_ROOT_PASSWORD` from `.env`).

## Generating & Deploying the Static Site

There are two buildable sites here — the original WordPress mirror in `wordpress-site/`, and the SvelteKit rebuild in `svelte-site/`. They are two versions of the same public site rather than two different sites, so only one is live at a time and `deploy.py` takes the name of the one you mean.

### Building

  - **SvelteKit** — `cd svelte-site && npm install && npm run build`, which prerenders to `svelte-site/build`.
  - **WordPress** — with the containers up, run `./wordpress-site/build.sh`, which writes `wordpress-site/build`.
    - Mirrors `http://localhost:8085/` with `wget`, then rewrites `PROD_URL` (set in `.env`) over the local dev URL throughout the mirrored files.
    - It also fetches WordPress's real 404 template and writes it to `build/404/index.html`, matching the folder-style layout the live site uses at `/404/` (wget's crawler never intentionally requests a broken link, so this needs its own fetch step). The SvelteKit build prerenders the same path as a normal route, so either way, point the CloudFront distribution's custom error response at `/404/index.html`.

### Deploying

  1. Set `BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY` in `.env`.
  2. Run `pip install -r requirements.txt` (once), then name the site to ship:

     ```sh
     python3 deploy.py svelte
     python3 deploy.py wordpress
     python3 deploy.py svelte --dry-run   # list the changes without uploading
     ```

     - Each runs `aws s3 sync <site>/build s3://$BUCKET_NAME --delete`, so removed pages/assets are cleaned up in the bucket too.
     - `--delete` makes the bucket match the chosen directory exactly, which is also why there is no default: deploying one site replaces the other. `--dry-run` shows what would change first.
     - It refuses to run if the build directory is missing or has no `index.html`, so a half-finished build can't empty the bucket.
  3. Requires the `aws` CLI installed locally (`brew install awscli`).
